# Authoring allowlist — skills that may grant authorisation to edit Salesforce
# metadata. One skill name per line. Blank lines and # comments are ignored.
#
# DERIVATION RULE (this, not the list, is the thing to preserve):
#   a skill belongs here when its subtree — INCLUDING the personas it dispatches
#   as subagents — writes Salesforce metadata.
#
# "Including personas" is load-bearing. Four personas write files, and each is
# owned by a skill that does not obviously author metadata by its own name:
#   sf-bug-reproduction-validator    -> sf-debug
#   sf-pr-comment-resolver           -> sf-resolve-pr-feedback
#   sf-deployment-verification-agent -> sf-review
#   sf-mcp-tool-builder-agent        -> mcp-tool-builder
# Derive by "what does the subtree write", never by "does the name say generate".
#
# THE LIST IS HAND-MAINTAINED, AND THE LINT IS ONE-DIRECTIONAL.
# `cli/src/lint/authoring-allowlist.ts` checks that every name here resolves to a
# real skills/<name>/SKILL.md, and that every routing-table target appears here.
# It CANNOT check the reverse — "a skill that writes metadata but is missing from
# this file" — because nothing in a SKILL.md mechanically declares that it writes
# metadata. Implementing that check needs a frontmatter marker on all 69 skills,
# which is cross-cutting work deliberately not done here.
# So: adding a skill that authors metadata means adding it here BY HAND. Nothing
# will catch the omission for you.
